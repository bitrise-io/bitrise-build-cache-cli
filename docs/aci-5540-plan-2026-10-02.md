# ACI-5540 — plan v2: dsymutil CAS shim + KEEP_CAS=YES

Context: `docs/aci-5540-investigation-2026-10-01.md` (field data) and `docs/aci-5540-repro-2026-10-02.md` (local repro + `## 2026-10-02 ld-opacity experiment`). Root cause and fix mechanism are proven; this plan is about shipping them.

---

## v2 revisions summary

What changed from v1 → v2 and the one-liner evidence for each:

- **ld intercept out of scope — now firmly justified, not just deferred.** Post-link Mach-O has zero `0~` strings, no `__DWARF` segment; all CAS ids live in `.o` files reached via N_OSO stabs. (`repro.md` ld-opacity experiment §Mach-O inspection.)
- **Post-link dSYM regeneration dropped as a fix shape.** Dsymutil-with-plugin on the unstripped Mach-O produces a dSYM within 0.17% of native cache-OFF, section-for-section with DWARF 5 restored. The intercept works end-to-end. (`repro.md` §Manual dsymutil with plugin + §Three-way comparison.) Kept only as the Phase-0-failure fallback (§8).
- **Swiftc arg manipulation dropped.** Proven unnecessary — the gap is dsymutil-side, not swiftc-side. The `.o` files are correct; they just carry CAS indirections dsymutil can't resolve without the plugin.
- **KEEP_CAS and the shim are now explicitly coupled.** v1 listed them as two in-scope items without stating the dependency. Build B2 in the original repro ran *with* `KEEP_CAS=YES` and still showed the warnings → KEEP_CAS alone fixes nothing. Shim without KEEP_CAS → plugin store may be wiped between archive sub-steps → shim can't resolve. Ship both or ship neither. (§1.)
- **Phase-0 go/no-go narrowed.** v1 Phase-0 was "do CAS flags work on dsymutil"; that is now proven. v2 Phase-0 is strictly "does `GenerateDSYMFile` reroute to a shim we install (PATH / toolchain farm / `DEVELOPER_DIR`)?" Named explicit fallback: post-xcodebuild-archive CLI hook that re-runs dsymutil against `<archive>/dSYMs/` using known-good flags. (§8.)
- **Rollout flipped from opt-out killswitch to opt-in pilot for release N.** v1 shipped on-by-default with env kill switch. v2 ships off-by-default behind `BITRISE_BUILD_CACHE_DSYMUTIL_CAS_SHIM_ENABLED=true`, enabled on Infinum + 2–3 pilot customers for release N, flipped on-by-default in release N+1. (§5 + §9.)
- **Toolchain-farm bit-rot semantics added.** If pattern (1) wins Phase-0: version-stamp farm with `xcode-select -p` + Xcode build-number, re-stage on mismatch; shim fails *open* (fall through to default toolchain / stock dsymutil) when sibling tools missing, never fails closed. (§5.)
- **Filtered-stderr backstop added to the shim.** Strip `warning: 0~.*: No such file or directory` + paired `note: while processing <id>` from stderr pass-through. Cheap safety net if partial resolution ever misses an id. (§4.)
- **Scope-leak worry on `cmd/xcode/xcodebuild.go` resolved by construction.** `assembleArgs()` already returns early at `cmd/xcode/xcodebuild.go:813` when cache off and skips `BuildCacheArgs(...)` entirely. If we land `TOOLCHAINS` + `KEEP_CAS` through `xcodeargs.CacheArgs`, cache-off / baseline paths auto-strip them — no new strip-logic in the wrapper main path, no co-location drift. (§2.)

## 1. Scope boundary + explicit coupling

**In scope — ship together, bound atomically:**

1. **dsymutil CAS shim.** Intercept Xcode's `GenerateDSYMFile` dsymutil invocation and prepend `-cas-plugin-path <libToolchainCASPlugin.dylib>` + `-cas <DerivedData>/CompilationCache.noindex/plugin`. Exec the real toolchain `dsymutil`.
2. **`COMPILATION_CACHE_KEEP_CAS_DIRECTORY=YES` default** injected via `xcodeargs.CacheArgs` so the plugin store survives from swiftc → dsymutil within one `xcodebuild` invocation.

**Explicit coupling (do not break):**

- **KEEP_CAS without shim** — fixes zero user-visible symptoms. The plugin store surviving is useless if nothing passes `-cas-plugin-path` to dsymutil.
- **Shim without KEEP_CAS** — plugin store may be wiped mid-archive (observed in Infinum: `actions.v1` gone between sub-steps); shim finds `-cas` directory but it is empty or incomplete → still partial `No such file`.
- Therefore: both land in the same CLI release behind the same opt-in flag. Rollback flips both off together.

**Out of scope — see §9 for non-goals.**

## 2. Where it lives

**New package:**

- `internal/xcelerate/dsymshim/`
  - `shim.go` — pure argv-rewrite logic: input argv + env + filesystem → output argv for the real dsymutil. Covers "argv already has `-cas-plugin-path`" idempotency, kill-switch env, feature-detect fallback (`dsymutil --help` lacks `-cas` → bypass).
  - `resolve.go` — plugin path + cas path resolution. Plugin: env override → `${DEVELOPER_DIR}/usr/lib/libToolchainCASPlugin.dylib` via `xcode-select -p` (never a hardcoded `/Applications/Xcode.app/...` — Bitrise CI stacks use versioned paths like `Xcode-26.6.0.app`). Cas-path: `${PROJECT_TEMP_DIR}/../CompilationCache.noindex/plugin` or `${DerivedData}/CompilationCache.noindex/plugin`, with a graceful "no cas-path known → emit only `-cas-plugin-path`" fallback.
  - `stderr_filter.go` — filtered-stderr backstop. Strip `^warning: 0~[A-Za-z0-9+/_=-]+==: No such file or directory$` and the immediately-following `^note: while processing 0~...$`. Everything else passes through unchanged.
  - `cmd` wrapper surfaced through the existing CLI binary as `bitrise-build-cache dsymutil-shim ...` (same pattern as the xcelerate proxy / ccache helper reusing the CLI binary; the on-disk shim is a shell script that `exec`s the CLI with that subcommand).

**New subpackage, conditional on Phase-0:**

- `internal/config/xcelerate/toolchain/` — only populated if Phase-0 picks pattern (1), the custom-toolchain farm. Stages `~/.bitrise-xcelerate/toolchains/com.bitrise.cas-shim.xctoolchain/` as a symlink mirror of `XcodeDefault.xctoolchain`, replacing `usr/bin/dsymutil` with the shim. Includes a version-stamp file (`stamp.json` with `xcode-select -p` + Xcode build number) and a `requireStage(logger, osProxy)` entrypoint that re-stages on stamp mismatch.

**Modified files:**

- `internal/xcelerate/xcodeargs/args.go` — add two keys to `CacheArgs`:
  - `COMPILATION_CACHE_KEEP_CAS_DIRECTORY: "YES"` (always, when cache on).
  - `TOOLCHAINS: "com.bitrise.cas-shim $(inherited)"` *only when* Phase-0 chose pattern (1) and the staged toolchain exists. Guarded by a fast-path file check.
  - These ride through `BuildCacheArgs(noSwiftCache)` which is already called behind `assembleArgs`'s cache-on gate (see §1 scope-leak note above). Nothing to strip elsewhere.
- `internal/config/xcelerate/activate.go` — mirror the `xcodebuildWrapperScriptContent` / `xcrunWrapperScriptContent` pattern with a `dsymutilWrapperScriptContent` and extend `addXcelerateCommandToPathWithScriptWrapper` (or its toolchain-farm equivalent, depending on Phase-0 outcome). Log one line: `Wrote dsymutil CAS shim: <path>`.
- `internal/config/xcelerate/deactivate.go` — unchanged; existing `removeXcelerateRoot` already covers `~/.bitrise-xcelerate/{bin,toolchains}`.
- `cmd/xcode/xcodebuild.go` — no changes. The strip-on-cache-off path is already handled upstream in `assembleArgs()`; adding keys through `CacheArgs` is enough. (This resolves devils-advocate concern #6 by construction.)

## 4. Shim design — robustness and backstops

The shim is passive by design. In order:

1. **Idempotency.** If input argv already contains `-cas-plugin-path`, pass through unchanged.
2. **Kill-switch.** If `BITRISE_BUILD_CACHE_DSYMUTIL_CAS_SHIM_DISABLED=1` set in env, exec real dsymutil with original argv.
3. **Feature detect** (cached in `~/.local/state/xcelerate/dsymutil-caps.json`, keyed by `dsymutil --version`). If `dsymutil --help` doesn't advertise `-cas`, bypass.
4. **Resolve plugin + cas-path.** On any resolution failure, log one `[bitrise-cas-shim]` line to stderr and bypass (exec real dsymutil, original argv).
5. **Fail-open** (if toolchain-farm mechanism). If the staged farm is missing a sibling tool, log and fall through to default toolchain. Never block the build.
6. **Prepend flags + exec real dsymutil** via its absolute path (`$DEVELOPER_DIR/Toolchains/XcodeDefault.xctoolchain/usr/bin/dsymutil`), piping stderr through the `0~`-warning filter.
7. **Filtered-stderr backstop.** The filter strips `warning: 0~<base64>==: No such file or directory` and the paired `note: while processing 0~...` lines only. Any other dsymutil stderr passes through byte-for-byte. Rationale: cheap safety net for partial resolution; nothing else emits that exact signature.

Setup phase (steps 1–5) has a hard ≤100ms budget. Any step exceeding falls through to bypass.

## 5. Backwards compat, rollout flag, rollback

- **Opt-in flag for release N:** `BITRISE_BUILD_CACHE_DSYMUTIL_CAS_SHIM_ENABLED=true` (naming follows existing `BITRISE_XCELERATE_*` / `BITRISE_BUILD_CACHE_*` convention; check `internal/config/xcelerate/paths.go` for the pattern and sibling an env constant on activate's side). When unset or false: activate skips writing the shim, skips `TOOLCHAINS` key, skips `KEEP_CAS` key — null feature.
- **Pilot cohort:** Infinum + 2–3 pilot customer workspaces for release N. Success criterion: `grep -c 'warning: 0~' <archive-log> == 0` across pilot archive builds. One release cycle at pilot scale before flipping default-on.
- **Release N+1 flip:** default `true` with the existing `BITRISE_BUILD_CACHE_DSYMUTIL_CAS_SHIM_DISABLED=1` as the opt-out killswitch (same env, inverted sense — set only when flag renames; otherwise keep two separate envs: `_ENABLED` for pilot, `_DISABLED` for post-flip rollback).
- **Toolchain-farm bit-rot** (if pattern (1) wins Phase-0):
  - Stage with a `stamp.json` capturing `xcode-select -p` + Xcode build number. `requireStage()` compares the current stamp before every activate; mismatch → nuke and re-stage. Keeps us correct across Xcode minor bumps.
  - Fail **open**: if a sibling tool symlink is missing (e.g. new Xcode added a `swift-foo` we didn't mirror), the shim logs and execs stock dsymutil via `$DEVELOPER_DIR`. Never fails the build. Documented as the only acceptable failure mode.
- **Deactivate** nukes `~/.bitrise-xcelerate/`. Shim + toolchain + stamp gone. One release cycle to roll back if a customer reports an issue — no persistent state outside the root.

## 8. Phase-0 go/no-go gate — "does GenerateDSYMFile reroute?"

**The only unknown left.** We have proved CAS flags + plugin produce a correct dSYM when dsymutil is invoked directly. We have **not** proved that any in-codebase intercept mechanism actually causes `GenerateDSYMFile` to invoke the shim instead of the stock toolchain `dsymutil`.

**Phase-0 experiment (first implementation sprint, ≤1 day):** write both intercepts, run `xcodebuild archive`, grep the log for a shim marker. Pick the first winner:

1. **PATH shim** at `~/.bitrise-xcelerate/bin/dsymutil`. Cheapest. SwiftBuild's `BuiltInCompilers.xcspec` has `dsymutil` unqualified — if resolution ever hits a PATH search, this works. Field evidence (`repro.md` log line 1947) shows resolution via absolute toolchain path, which **suggests this will miss** but needs a 30-min empirical confirmation.
2. **Custom toolchain farm + `TOOLCHAINS=com.bitrise.cas-shim $(inherited)`.** Documented pattern (Tuist uses it). Larger surface (symlink farm, stamping, re-stage on Xcode bump).
3. **`DEVELOPER_DIR` override** pointed at a mirrored farm. Smaller than (2) but same symlink surface.

**Fallback if all three fail:** `post-xcodebuild-archive` CLI hook. The wrapper, after a successful `xcodebuild archive`, invokes dsymutil ourselves against every binary under `<archive>/dSYMs/` (or re-reads `Products/Applications/*.app/*` with the unstripped Mach-O from DerivedData — see `repro.md` §Attempt to re-generate the dSYM for why the stripped archive binary is insufficient on its own; we need to point dsymutil at the pre-strip binary in `Build/Products/`). Clean, no shim, no toolchain farm, but requires the wrapper to find the unstripped binary and regenerate the dSYM in-place over Xcode's output.

Fallback has one real cost: an extra ~5–20s per archive on top of Xcode's own dsymutil run (we re-dsymutil what Xcode just dsymutil'd). Acceptable for correctness; measure and document.

**Non-fallback (removed from v1):** post-link regeneration as the *primary* fix. We proved intercept works; using the fallback as primary trades a daemon-like shim surface for a wrapper-side one, which is not a win.

## 9. Explicit non-goals

- **No ld shim.** Firmly: ld-opacity experiment confirmed post-link Mach-O carries zero CAS data and no DWARF segment. The entire gap is dsymutil-side.
- **No swiftc arg manipulation.** The `.o` files produced under cache replay are correct for Apple's own pipeline; dsymutil just needs the plugin to resolve the indirections swiftc wrote. We lose nothing by keeping compile-cache replay as-is.
- **No post-link dSYM regeneration as primary.** Only as the Phase-0-failure fallback (§8).
- **No upstream SwiftBuild patch** in this ticket — file Apple Feedback with `repro.md` as attachment; non-blocking follow-up.
- **No custom LLVM-CAS plugin.** Reserved for the separate larger work tracked in `docs/xcode-cas-plugin-fork-analysis-2026-10-01.md`.
- **No SPM-target IDE coverage.** Unrelated gap tracked separately in `docs/xcode-app-ide-remote-cas-findings-2026-09-30.md`.
- **No doctor subcommand change.** Shim is passive; doctor already lists `~/.bitrise-xcelerate/bin/`.
- **No `blobstats` schema change.** Transfer behaviour unchanged.

## 10. Risks + open questions

1. **Phase-0 intercept resolution.** The one real unknown. Mitigation: §8 experiment + explicit fallback.
2. **Older Xcode `-cas-plugin-path` support.** Confirmed on 26.6 / 27.0. Not spot-checked on 15.x. Shim's `--help`-feature-detect bypass handles unsupported case; add a Xcode 15 CI matrix entry if we want higher confidence.
3. **Plugin path discovery across Xcode locations.** Resolved via `xcode-select -p` + `/usr/lib/libToolchainCASPlugin.dylib`. Runs in the shim at exec time, not activate time (Xcode selection can change between activate and build).
4. **`TOOLCHAINS=` user-set collisions.** We must *prepend* `com.bitrise.cas-shim $(inherited)` (never overwrite). Covered by a wrapper test.
5. **`KEEP_CAS=YES` disk footprint.** Observable in local-dev. Apple's `COMPILATION_CACHE_LIMIT_SIZE` is noted as "a lie" in the plugin fork analysis — monitor; add wrapper-side GC only if field reports show disk pressure.
6. **Deactivate while Xcode.app has a build in flight.** If pattern (1) wins Phase-0 and Xcode is mid-build with our `TOOLCHAINS` active, deactivation would remove the staged toolchain mid-link. Mitigation: deactivate logs a warning if Xcode.app PID is running. Low likelihood in CI (deactivate is a step boundary).
7. **Toolchain-farm bit-rot across Xcode minor bumps.** Mitigated by stamp + re-stage + fail-open (§5).
